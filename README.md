# Sales Operations Automation Pipeline
 
An end-to-end pipeline that takes messy sales exports from three systems (a CRM,
a point-of-sale system and a wholesale SFTP feed), cleans them automatically,
restructures them into a star schema, computes the KPIs a sales operations team
asks for, and sends the team an automatic email through Zapier after every run.
 
It was built to show how I approach operational data problems end to end:
not just the analysis, but the cleaning, the audit trail, the reporting and the
hand-off to the people who use the numbers.
 
> **Data note:** all data in `data/` is synthetically generated by
> `scripts/01_generate_raw_data.py` for portfolio purposes. It does not
> represent any real company, customer or transaction. Every number below is
> produced by the scripts in this repo, not typed by hand, and the run is seeded,
> so you can reproduce it exactly (see *How to run it*).
 
---
 
## Highlights
 
- **Saved an estimated 17 hours of manual prep per run** by automating the cleaning of 53,560 rows from CRM, POS and SFTP exports and resolving 4,166 data issues, including 1,560 duplicates, with **0 rows lost**.
- **Engineered a star schema and automated KPI reporting** ($38.9M revenue, 51,744 orders, top 10 of 1,341 customers at 33.3%) with an audit log of every fix.
- **Replaced manual checks with real-time Zapier email alerts** that notify the team after every run.
---
 
## The problem
 
Teams that pull sales data from more than one system almost always face the
same issues: the same order exported twice, dates written in different formats,
prices stored as text, and missing names, regions or prices. Someone has to fix
all of it by hand before any report can be trusted. That work is slow,
error-prone and does not scale.
 
## What the pipeline does
 
```
3 raw source exports (CRM / POS / SFTP)
        |
        v
01_generate_raw_data.py        synthetic data generator (stands in for real exports)
        |
        v
02_clean_and_restructure.py    ---> data/processed/dim_customer.csv
   - parses 3 different date formats       dim_product.csv
   - parses currency stored as text        dim_date.csv
   - removes duplicate orders              fact_sales.csv
   - standardizes region names             data_quality_log.csv  (every fix, logged)
   - fills or flags missing values
     (never drops a row without logging why)
        |
        v
03_generate_report.py          ---> outputs/sales_report.xlsx
   - computes KPIs                       (Summary, Top Customers, Region Breakdown,
   - writes the Excel report              Monthly Trend, Data Quality Log tabs)
                               ---> outputs/zapier_trigger_row.csv
                               ---> outputs/run_summary.txt
        |
        v
Google Sheet run log  --->  Zapier  --->  automatic email to the team
```

### What the 4,166 data issues were
 
Taken directly from `data/processed/data_quality_log.csv`:
 
| Cleaning step | Rows | What happened |
|---|---|---|
| Remove duplicates | 1,560 | Same order exported twice; one copy kept |
| Standardize region | 1,041 | Missing or unmapped region set to "Unknown" (flagged, not dropped) |
| Fix missing customer name | 786 | Backfilled from the customer ID so the row stays usable |
| Fill missing price | 523 | Filled with that product's median observed price |
| Flag returns | 256 | Negative quantities kept and flagged, excluded from revenue |
| Unparseable dates | 0 | All three date formats parsed |
| Unrecoverable rows dropped | 0 | Nothing lost |
 
The 4,166 counts **fixes**, not unique rows: a row with two problems is counted twice.
 
### Validating the pipeline against its own input
 
Because the input is synthetic, the pipeline can be checked against known truth:
the generator injects exactly **1,560 duplicates** (3% of 52,000 orders), and the
cleaning step removes exactly **1,560**, keeping all **52,000** real orders.
 
An earlier version generated order IDs at random, so about 1,450 different orders
shared an ID by chance. That made the dedupe step delete real orders and
undercounted total orders. Order IDs are now drawn without replacement, and the
injected and removed duplicate counts match exactly.
 
### How the time estimate works
 
`03_generate_report.py` assumes a conservative **15 seconds** for a person to
find, check and fix one bad record by hand in Excel:
 
> 4,166 fixes × 15 seconds ÷ 3,600 ≈ **17.4 hours per run**
 
This does not include the time to open, combine and re-check the three exports,
so the real manual effort would likely be higher.

## The automation, live
 
The pipeline writes a one-row run summary (`outputs/zapier_trigger_row.csv`).
That row is added to a Google Sheet, and a live Zap emails the team the headline
numbers. Nobody has to open the workbook to know a new report is ready.

## Tech stack
 
| Layer | Tools |
|---|---|
| Ingestion and cleaning | Python, pandas, NumPy |
| Data model | Star schema: `fact_sales` + `dim_customer`, `dim_product`, `dim_date` |
| Reporting | openpyxl (formatted multi-tab Excel workbook) |
| Automation | Zapier (Google Sheets → Gmail, no code) |
| Downstream use | Clean CSVs load directly into Power BI or Excel Power Query |
 
## How to run it
 
```bash
pip install -r requirements.txt
python scripts/01_generate_raw_data.py       # creates the messy source files
python scripts/02_clean_and_restructure.py   # cleans data + builds the star schema
python scripts/03_generate_report.py         # computes KPIs + writes the report
```
 
Outputs land in `data/processed/` and `outputs/`. Every script is seeded, and
`requirements.txt` pins exact library versions, so a re-run reproduces the
numbers above.
 
## Connecting the Zapier layer yourself
 
1. Create a Google Sheet named `automation_run_log` with the columns in
   `outputs/zapier_trigger_row.csv`: `run_timestamp`, `raw_rows_ingested`,
   `clean_rows_written`, `records_auto_cleaned`, `total_revenue`,
   `top10_customer_share`, `est_manual_hours_saved`, `status`.
2. After each run, add `outputs/zapier_trigger_row.csv` to the sheet as a new row
   (by hand while testing, or with the Google Sheets API for a fully hands-off
   version).
3. In Zapier: **Trigger** → Google Sheets → *New Spreadsheet Row* →
   `automation_run_log`. **Action** → Gmail → *Send Email*, using the row's fields.
4. Turn the Zap on. Every new run now emails the team automatically.
In production, the Python scripts would run on a schedule (cron, Task Scheduler
or Airflow), and Zapier would handle distribution and alerts.
 
## Why this matters for an operations role
 
Operations and analytics teams often need someone who can read and change
Python for reporting, work in advanced Excel, and connect systems with no-code
tools like Zapier. This project shows all three on one problem, end to end,
with an audit trail so anyone can check how each number was produced.
